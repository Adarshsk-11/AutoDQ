# Testing

## Synthetic datasets (A–H)

Generated by `datasets/generate_datasets.py`, each designed to isolate one data quality
problem so we can verify AutoDQ actually detects what it claims to detect (spec §17):

| Dataset | Rows×Cols | Designed problem | Injection method |
|---|---|---|---|
| A_clean.csv | 1000×4 | None (baseline) | — |
| B_missing_values.csv | 1000×4 | Missing values | 15% of `feature_1`, 30% of `category` set to NaN |
| C_class_imbalance.csv | 555×4 | Class imbalance (~1:9) | Minority class downsampled to 11% |
| D_duplicates.csv | 1008×4 | Duplicate rows | 12% of rows re-appended as exact copies |
| E_outliers.csv | 1000×4 | Statistical outliers | 5% of `feature_1` multiplied by ±8 |
| F_redundant_features.csv | 1000×5 | Redundant/correlated features | `feature_1_copy` = `feature_1`×1.02 + small noise (corr ≈0.98) |
| G_leakage.csv | 1000×5 | Potential data leakage | `target_echo` directly encodes the target (0.01/0.99 + noise) |
| H_combined_problems.csv | 621×6 | All of the above combined | Imbalance + missing values + outliers + redundancy + leakage + duplicates stacked |

## Unit tests

`backend/tests/test_core_engine.py`, 39 tests, all passing:

- **Per-dataset detection tests** (`test_dataset_a_..` through `test_dataset_h_..`):
  confirm each synthetic dataset trips the specific detector(s) it was designed to
  trigger, and that dataset A (clean) does **not** false-positive on missing values or
  duplicates.
- **Directional validity** (`test_directional_validity_missing_values_lower_dqi`,
  `test_dataset_h_combined_scores_lower_than_clean`): confirms that degrading a dataset
  measurably lowers its DQI — the core empirical claim the project needs to demonstrate
  (spec §26), without overclaiming statistical proof.
- **Formula unit tests** (`test_completeness_formula`, `test_uniqueness_formula`,
  `test_balance_perfectly_balanced_binary`, `test_dqi_weights_sum_and_redistribution`):
  verify the exact arithmetic of each metric against hand-computed expected values.
- **Baseline ML tests** (`test_baseline_runs_cross_validation_with_mean_and_std`,
  `test_baseline_excludes_leakage_feature_and_shows_both_runs`,
  `test_baseline_excludes_one_of_redundant_pair`,
  `test_baseline_no_exclusions_on_clean_dataset`): confirm cross-validated metrics are
  reported as mean/std pairs, that leakage-flagged columns are excluded from the
  "cleaned" comparison run and measurably lower its inflated performance, that only one
  column from a redundant pair is dropped (not both), and that a clean dataset with
  nothing flagged doesn't produce a spurious second run.
- **Error-handling / edge-case tests** (spec §15), each asserting the pipeline
  completes without raising: empty DataFrame, no target column, an entirely-missing
  column, a single-class target, a constant column, a 2-row dataset, an all-numeric
  frame, an all-categorical frame, a datetime column, and undefined correlation on
  constant columns. Also covers ingestion edge cases: malformed JSON structures,
  unsupported file extensions, and empty files.
- **Multiple-comparisons correction tests** (`test_bh_correction_suppresses_false_positives_in_wide_random_data`,
  `test_genuine_redundancy_still_detected_with_bh_correction`): confirm Benjamini-Hochberg
  correction actually suppresses chance correlations in a wide (40-column) random
  dataset while continuing to detect genuine strong correlations in the existing
  test datasets.
- **Multivariate leakage probe tests** (`test_multivariate_leakage_catches_xor_combination`,
  `test_multivariate_probe_stays_quiet_when_univariate_already_flagged`,
  `test_multivariate_probe_quiet_on_clean_dataset`): confirm the model-based probe
  catches an XOR-style combination that univariate correlation cannot see (verified
  by first asserting the individual correlations ARE weak), stays quiet when a
  univariate leakage finding already explains the result, and produces no false
  positives on a clean dataset.
- **Informativeness diagnostic tests** (`test_informativeness_not_part_of_dqi_components`,
  `test_informativeness_ranks_real_signal_above_pure_noise`,
  `test_informativeness_unavailable_without_target`): confirm the diagnostic is
  genuinely separate from the five DQI components (not silently folded in), correctly
  ranks a truly informative feature above pure noise, and reports unavailable rather
  than crashing when no target exists.

Run them with:

```bash
cd backend
pytest tests/ -v
```

(In the development sandbox used to build this MVP, `pytest` itself wasn't installable
due to no network access, so the same test functions were executed via a small
stdlib-only shim reproducing `pytest.approx`/`pytest.raises`, confirming **39/39 pass**.
On your machine, with network access, plain `pytest tests/ -v` will run them directly —
no shim needed.)

## Running the cross-dataset validation harness

Beyond the unit tests above, `datasets/validation_harness.py` provides a way to
sanity-check the DQI-vs-performance relationship on any dataset you have available:

```bash
cd datasets
python validation_harness.py A_clean.csv target --levels 5
python validation_harness.py demo_customer_churn.csv churn --levels 5
```

Each run degrades the dataset at 5 intensity levels and reports the Pearson
correlation between DQI and cross-validated baseline performance across those
levels. See `docs/math_and_logic.md` §12 and `docs/limitations_and_future_validation.md`
for the actual results this produced and what a fuller validation study would still
require.

## A real bug this test suite caught mid-development

While adding the leakage-aware baseline comparison, the existing "ID-like column"
heuristic (`nunique >= 98% of rows`) turned out to be silently misclassifying ordinary
continuous numeric features (which are naturally almost-all-unique across rows) as
identifier columns. Two consequences, both now fixed:

1. The baseline model was dropping genuine continuous features from training entirely,
   rather than just genuine ID columns.
2. The leakage detector was flagging every continuous feature as "potential leakage"
   purely for having high cardinality — a false-positive generator, not a real signal.

The fix (`app/utils/column_heuristics.py::is_id_like_column`) only classifies a column
as ID-like if it's high-cardinality **and** either (a) integer-valued with a name
suggestive of an identifier (`id`, `uuid`, `index`, etc.), or (b) a high-cardinality
categorical/text column (which is effectively free text or a generated string
identifier). A continuous float column with a normal feature name is never treated as
an ID column. This is used consistently across the baseline model, leakage detection,
and near-duplicate detection in uniqueness scoring.

## Demo dataset: `demo_customer_churn.csv`

A polished, realistic customer-churn dataset (2000 base rows, ~2120 after injected
duplicates) built specifically for the live demonstration, with a controlled, documented
set of quality problems:

1. **Missing values** — ~8% of `monthly_charges`, ~5% of `contract_type`
2. **Duplicate rows** — 6% of rows re-appended as exact duplicates
3. **Outliers** — 8 rows with impossible `age` values (150, -5, 999) simulating data-entry
   errors
4. **Redundant feature** — `estimated_annual_value` ≈ `monthly_charges` × 12 (correlation
   should trip the ≥0.90 redundancy threshold)
5. **Potential leakage** — `retention_flag` = `1 - churn` (a near-perfect inverse of the
   target that would never be legitimately available before prediction time)

The underlying churn signal itself is genuinely learnable (driven by contract type,
tenure, and support call volume with added noise), so the baseline model on this dataset
should show non-trivial-but-imperfect performance — useful for showing that fixing the
injected leakage feature changes the picture (with it included, accuracy/F1 will look
suspiciously perfect; with it excluded, more realistic).

## Validating directional DQI behavior live in the demo

To show DQI moving in the right direction during a live demo (spec §27 step 13-14):

1. Analyze `A_clean.csv` (target `target`) — note the DQI and F1.
2. Analyze `H_combined_problems.csv` (target `target`) — DQI and the baseline model's F1
   should both be visibly lower, since this dataset combines missing values, imbalance,
   outliers, redundancy, and leakage on top of the same underlying signal.
3. Point out in the Issues tab which specific problems account for the drop.

This demonstrates the intended empirical relationship (worse data → lower DQI → often
worse model performance) without claiming a proven causal/statistical relationship —
exactly the framing the project spec asks for.
